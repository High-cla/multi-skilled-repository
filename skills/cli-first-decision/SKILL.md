# CLI-First Decision 3.3

## 1. 目标与原则

目标：以最少的工具往返、最短的关键路径和最低的上下文/资源成本，可靠地完成用户目标；对具体代码实现，默认以运行速度和峰值内存优先。

- 先判断任务，再选择工具；不为使用 CLI 而使用 CLI。
- 本地文件操作优先 FastCtx；终端组合与批处理优先 CLI。
- 结构匹配优先 ast-grep；符号关系优先 codebase-memory。
- 先复用项目原生 API，再考虑额外 wrapper。
- 无依赖操作同轮并行；可管道合并的操作优先合并。
- 并行必须考虑调用成本、限流、上下文和写入冲突。
- 具体代码实现优先追求更短运行时间和更低峰值内存，先分析复杂度/理论下界，再用基准与剖析迭代逼近最优。\n- 写操作范围明确、修改最小、可验证、可恢复。
- 工具返回成功不等于业务成功；完成必须有证据。

## 2. 触发、技能优先与例外

多步骤任务、工具选型、并行/委派决策、批量操作或跨模块工作时，执行本技能的快速路由。

技能触发优先于本技能的通用建议。命中具体领域时，先加载对应技能，再按本技能选工具：

| 意图 | 先加载的技能 |
|---|---|
| 结构搜索、规则、pattern、批量代码改写 | ast-grep |
| 符号、调用链、依赖、影响面、架构 | codebase-memory |
| 工具选择、并行、调用合并、是否委派 | cli-first-decision |
| 写或改代码 | clean-code、coding-standards |
| Bug、复现、报错定位 | systematic-debugging |
| 写计划或执行计划 | writing-plans、executing-plans |
| 代码审查 | requesting-code-review、receiving-code-review、code-review |
| 长任务或跨会话续跑 | long-task-continuation |
| 多子智能体并行 | dispatching-parallel-agents、subagent-driven-development |
| JSON/YAML 解析 | jq-query |
| HTTP/API 调试 | git-curl |
| 文件查找/全文搜索/模糊过滤 | fd-find、rg-search、fzf-filter |
| Windows CMD/PowerShell 脚本 | cmd-powershell-pitfalls |

例外：一句话可直接回答、纯读取状态、已知路径的简单读取、单文件小改，不必为了形式加载本技能或额外技能。

同一会话同一技能只加载一次。跨领域任务只加载主轴必需技能，不堆叠无关技能。若运行环境没有技能加载机制，不要伪造加载成功；直接采用已知规则。

## 3. 六步决策流程

### Step 1：分类任务

| 类型 | 默认路径 |
|---|---|
| 单个已知文件读取 | FastCtx inspect_local_file |
| 多个已知文件读取 | 一次 inspect_local_file 批量传 files |
| 文件名查找 | FastCtx glob；CLI fd |
| 普通文本搜索 | FastCtx grep；CLI rg |
| 语法/代码结构搜索 | ast-grep（sg CLI） |
| 符号、引用、调用链、影响面 | codebase-memory |
| 机械式跨文件替换 | FastCtx replace；或经验证的 sd |
| 语义重写/少量局部编辑 | 内置 edit/write |
| JSON/YAML 处理 | jq / yq |
| HTTP 调试 | curl / git-curl |
| 长时间命令 | FastCtx run_background |
| 独立复杂调研/审查 | 评估收益后并行委派 |

### Step 2：检查工具真实可用性

调用前检查当前运行环境实际注册的工具名称、参数 schema、权限和返回格式。

- 只使用当前工具列表或已验证环境中存在的工具。
- 不臆造 MCP 名称、CLI 参数、agent 类型或 PTC SDK API。
- 不把其他 harness 的工具当成当前环境可用工具。
- 工具不可用时，转向已存在的等价路径；无法替代时明确报告阻塞。
- 不因工具名称熟悉就跳过 schema 检查。

### Step 3：建立依赖图

将任务表示为 DAG：

- 节点：一次工具调用或一个执行步骤。
- 边：数据依赖、状态依赖、接口依赖或写入冲突。
- 无依赖节点：可放入同一并行批次。
- 有依赖节点：按拓扑层级执行。
- 同一文件或共享状态的写入：串行化。

优先完成能够解锁最多后续步骤、且成本最低的操作。

### Step 4：选择最短工具路径

依次判断：

1. 项目是否已有原生 API/脚本可直接完成？
2. FastCtx 是否已有对应的文件或终端能力？
3. 是否可以通过一条 CLI 管道完成？
4. 问题是否要求 AST 或符号关系？
5. 是否存在真实独立且值得委派的子任务？
6. 是否能由一个内置工具调用直接完成？

路由优先级是任务相关的，不是全局固定排名。不得为了“CLI-first”增加不必要的 CLI 往返。

### Step 5：执行

- 同源、同类型批量请求优先一次调用。
- 无依赖调用同轮并行。
- 可管道组合的步骤合并为一条命令。
- 有依赖的步骤分层执行。
- 写入前明确文件集合、修改范围和冲突策略。

### Step 6：验证并结束

检查工具状态、输出完整性、实际副作用和验收条件。只报告真实执行并验证过的结果。

## 4. FastCtx 优先：本地文件与命令

本地文件和终端操作优先 FastCtx。不要使用 shell 等价物替代 FastCtx 的专用文件工具。

| 场景 | 首选工具 | 使用规则 |
|---|---|---|
| 读取文件 | inspect_local_file | 已知路径直接读取 |
| 批量读取 | inspect_local_file | 一次传 files=[{path:...}, ...] |
| 全文搜索 | grep | 限定目录、文件类型和上下文 |
| 文件查找 | glob | 优先 glob 模式而非递归列目录 |
| 跨文件机械替换 | replace | 先 dry-run；保留编码和行尾；检测并发修改 |
| 终端命令 | run | POSIX Bash、非交互、无 TTY |
| 长任务启动 | run_background | 预计超过 run 四分钟上限时使用 |
| 后台任务状态 | job_list / job_output | 以 job_id 查询 |
| 停止后台任务 | job_kill | 先确认目标 job_id |

### 文件读取规则

- 只读任务只读取回答问题必需的文件。
- 多个文件一次 inspect_local_file 调用，除非文件依赖关系要求分阶段。
- 工具结果最后一行若为 Complete，停止续读。
- 结果为 Partial 时，只按其附带的参数原样续读，不自行推导参数。
- 文件引用即使是 URI 形状，也传等价的普通绝对路径。
- 不要把大文件全文读入上下文；先 grep 定位，再读取相关范围。

### 批量修改规则

- 机械替换用 FastCtx replace，先预览。
- 语义重写或少量局部修改使用 edit/write。
- 不逐个 Edit 完全同构的机械修改。
- 写入前检查文件是否被其他进程更改；工具支持并发保护时必须使用。
- 修改后检查 diff、命中数量和残留项。

### Shell 规则

FastCtx run 执行 POSIX Bash；Windows 上也写 Git Bash 兼容语法：

- 不写 PowerShell 语法。
- 命令必须非交互；使用 --yes、--no-edit 等等价选项。
- 编辑器和分页器默认禁用。
- 不依赖 TTY。
- 输出保持必要且有限。
- 非零退出码是需要分析的结果，不等于工具崩溃。
- 同时检查 stdout、stderr、退出码和 Complete/Partial 状态。
- 超过四分钟的命令用 run_background，之后通过 job_output/job_list 查看；不等待一个长命令占满前台调用。

推荐的安全管道：

```bash
fd -0 -e ts src | xargs -0 -r rg 'AuthService'
```

带空格或特殊字符的路径使用 NUL 分隔；避免未经转义的命令字符串拼接。

## 5. CLI 选择矩阵

CLI 在 FastCtx 的 run 中执行，不能假设所有命令已安装；必要时先做一次低成本可用性检查。

| 任务 | 首选 | 说明 |
|---|---|---|
| 文件查找 | fd | 优于递归 find |
| 文本搜索 | rg | 优于逐文件读取或普通 grep |
| 结构搜索/改写 | sg（ast-grep） | 语法结构匹配，不用正则冒充 AST |
| 批量文本替换 | sd | 仅适用于纯文本且不依赖语法结构 |
| 批量文件操作 | FastCtx replace | 保留编码/行尾并支持 dry-run/并发保护 |
| JSON | jq | 查询、过滤、聚合 |
| YAML/XML | yq | 使用已安装版本的正确输入格式参数 |
| HTTP | curl | 先检查状态码和错误体 |
| 模糊过滤 | fzf | 大结果集交互筛选；非交互时优先 --filter |
| 代码统计 | tokei；简单计数用 wc | 只在统计有助于决策时执行 |
| 结构化 diff | difft | 重构审查 |
| Git diff 展示 | delta | 仅改善可读性，不改变 diff 事实 |
| 压缩文件搜索 | rg -z / zstd -d -c | 先确认实际格式 |
| JSONL 聚合 | duckdb | 必要时先流式解压 |
| 任务编排 | just | 先读项目 justfile 或 --list |
| MCP CLI 退路 | mcp2cli @<name> | 仅限已 bake 且当前可用的 MCP；先查 help/schema |

不要为一次简单操作引入新依赖。CLI 不存在时，选择已注册的 FastCtx 或内置工具；不要静默安装工具。

## 6. ast-grep：结构搜索与规则开发

当查询涉及代码形状、语法节点、函数调用结构、API 调用模式或批量代码重构时，优先加载并使用 ast-grep 技能，执行 sg CLI。

规则开发流程：

1. 将用户查询拆分为更小的代码匹配目标。
2. 确认语言、文件范围和目标语法节点。
3. 识别可独立测试的子规则。
4. 使用关系规则或组合规则组织子规则。
5. 用最小示例测试规则。
6. 不匹配时逐个移除子规则，定位不匹配的约束。
7. 必要时转储 AST 或模式查询，检查实际语法结构。
8. 测试正例、反例和边界情况。
9. 预览 rewrite 结果，核对命中数量和差异。
10. 验收后才执行批量修改。

规则：

- 结构问题不用正则硬改代码。
- 普通文本、日志和 Markdown 搜索使用 rg/grep，不滥用 AST。
- Windows DSH 环境运行 sg 时，按本机工具契约使用 C:/... 形式的路径。
- 搜索命中不自动代表重写安全；必须检查变更结果。

## 7. codebase-memory：符号与依赖分析

当任务涉及符号、调用链、依赖、架构或影响面时，优先加载并使用 codebase-memory 对应工具。

建议流程：

1. 定位符号及其定义。
2. 查找调用者和被调用者。
3. 查询模块依赖和关键边界。
4. 将结果转成待检查文件/符号清单。
5. 用 FastCtx、rg 或 sg 交叉验证相关源码。
6. 根据源码和测试确定真实影响面。

图谱是辅助索引，不是源码事实来源。索引可能过期或不完整；发现缺失、冲突或疑似陈旧时，以当前源码、构建配置和测试为准，并报告索引限制。

## 8. 没有 GitHub / Context7 插件时

GitHub 和 Context7 插件不是本技能的依赖，也不得假设它们已安装。

### 远程 Git 仓库

- 本地已有 clone：用 git、FastCtx 和项目脚本处理。
- 公开仓库只读：可用当前可用的浏览器/Web 工具，或 curl 访问公开的官方页面/API。
- 远程写入：必须存在已认证的 git/CLI/API 通道及所需权限；否则说明阻塞，不得声称已修改。
- 不要把 GitHub 插件工具名写成必需工具，也不要假设 gh CLI 已安装。

### 第三方库文档

- 优先项目 lockfile/package manifest 确认版本。
- 再查该版本的官方文档、官方仓库和发布说明。
- 只有当前工具列表确实存在 Context7 时才使用 Context7。
- Context7 不可用时，不得臆造 resolve/query 工具；改查官方资料或明确说明未能验证的 API。

所有外部资料都必须区分已验证事实、推断和未知项。

## 9. 并行、管道与调用合并

### 决策表

| 依赖/冲突 | 策略 |
|---|---|
| 无依赖的只读调用 | 同轮并行 |
| 同源数据且 API 支持批量 | 一次批量调用优先于 N 次并发 |
| 能通过 stdin/stdout 串联 | 一条 CLI 管道 |
| 有数据依赖 | 分层；层内并行、层间串行 |
| 写入不同文件且无共享依赖 | 可并行 |
| 写入同一文件 | 必须串行 |
| 消费另一个任务尚未确定的接口/输出 | 先确定生产者结果，再执行消费者 |
| 多维独立审查 | 并行审查，统一汇总 |
| 共享状态或不可逆外部副作用 | 串行并加强检查 |

并行前计算实际收益：节省的关键路径时间必须大于启动、协调、限流、上下文和结果合并成本。并发数量服从工具服务限制，不设虚构的固定并发数。

### 写入边界

派发前记录每个执行者的 Read、Write 和共享接口范围。写入集合有交集时拆开或串行化；只读任务即使读取相同文件也可并行，但应限制重复输出。

禁止：

- 两个执行者同时编辑同一文件。
- 消费尚未稳定的接口。
- 把独立的批量文本替换委派给代理。
- 为单文件小改启动子智能体。
- 为形式上的“全并行”制造额外调用。

## 10. PTC TypeScript SDK 编排

### 10.1 默认使用方式

当当前 DSH 会话运行在 PTC preset，且提示上下文提供 `tools:sdk` 与 `run_code` 时，多步骤工具任务优先使用 PTC SDK 编写一个 TypeScript 程序组合，而不是把每个子步骤拆成多轮模型工具调用。

- `run_code` 是 PTC 程序的传输入口。
- `tools:sdk` 是运行时根据当前 agent 可见工具注册表生成的类型化 SDK。
- 在程序中通过 `tools.<工具名>(args)` 调用 SDK 中实际提供的绑定。
- 工具名、参数和返回类型必须以当前会话注入的 SDK 定义为准；不得从其他项目、旧版本或记忆中猜测。
- PTC-only 模式下，不要绕过 `run_code` 直接调用具名工具；应通过 SDK 绑定进入工具执行流水线。
- `tools:sdk` 不是外部安装的 GitHub/Context7 插件，也不是进程外驱动 Harness 的 `packages/sdk`；它是 PTC 工具呈现层生成的调用 SDK。

如果当前会话不是 PTC preset，或没有注入 `tools:sdk`，就使用当前真实可用的原生工具调用路径。不要假装 SDK 存在，也不要仅为简单单步操作强行切换模式。

### 10.2 何时使用 PTC

适合：
- 读多个文件后在程序内筛选、提取、归纳。
- 多个工具按依赖顺序串联，且中间结果只供程序判断。
- 根据中间结果执行条件分支、循环或批量处理。
- 扇出多个独立调用，再在程序内聚合结果。
- 希望仅把最终摘要或必要结果送回模型上下文。

不必使用：
- 单个简单工具调用。
- 必须由模型观察中间结果后再作高层判断的阶段。
- 用户要求逐步确认或每一步都有外部副作用审批的任务。
- PTC SDK 未提供所需工具或权限的任务。

### 10.3 编排模式

先读取当前会话的 `tools:sdk`，确认每个绑定的真实名称、参数、返回类型和可见性，再写程序。

示例仅演示结构，假设当前 SDK 确实提供 `tools.read_file({ path })`，并且对应参数被调度器判定为可并发：

~~~~ts
const paths = [
  "/project/src/auth.ts",
  "/project/src/router.ts",
  "/project/package.json",
];

const contents = await Promise.all(
  paths.map((path) => tools.read_file({ path }))
);

// 中间结果留在程序内部，只返回模型真正需要的摘要。
return contents.map((content, index) => ({
  path: paths[index],
  preview: content.slice(0, 1200),
  chars: content.length,
}));
~~~~

若当前 SDK 中没有 `read_file` 或参数不同，必须按注入的签名替换示例；不得把示例名称当成 DSH 固定内置工具。

### 10.4 并发语义

`Promise.all` 表示程序发起并发意图，不代表所有子调用都会并行执行：

- 只有工具对当前参数明确被标记为 concurrency-safe，才允许实际重叠执行。
- `isConcurrencySafe(args)` 必须明确返回 `true` 才能进入 parallel；未声明、未知、非法或判断异常均按 exclusive 处理。
- exclusive 子调用形成串行屏障；不要把有顺序依赖的写操作放进并行批次。
- 实际并发上限由 `maxParallelSubCalls` 运行时配置控制；参考实现默认值为 10，执行时以当前环境配置为准。
- 即使多个调用在程序中并发发起，工具执行策略、权限检查和最终结果顺序仍由 DSH 工具流水线管理。

### 10.5 结果与上下文

- 子调用的中间值保留在 PTC 程序内。
- 只有程序外层 logs 和 return value 返回模型上下文。
- 程序内完成筛选、映射、聚合，只返回决策所需字段。
- 不要把大文件、完整搜索结果或重复原始输出全部 return。
- 需要审计的工具操作仍经过完整工具流水线；不要把“中间结果不进上下文”误解为“没有执行记录”。

### 10.6 错误和副作用

- SDK 绑定调用失败会在程序内表现为 `ToolCallError`；可捕获并读取 `toolName` 定位具体失败工具。
- PTC 程序自身运行失败会作为结构化 `CODE_RUN_FAILED` 结果返回，检查具体错误后再调整程序。
- 一个绑定调用失败不代表此前的普通副作用已回滚；不要假设 PTC 提供事务。
- 程序结束/失败时，运行时会取消并 drain 未完成的绑定调用，但已经产生的外部副作用仍需按工具语义处理。
- 对写入、提交、发布、删除等非幂等操作，先完成只读预检；将可并行的只读部分与写入阶段分开；失败后先检查实际状态，不盲目重跑。
- 对多个文件写入，使用明确文件边界并串行处理共享文件；按工具契约验证每个写入结果。

### 10.7 运行时安全边界

PTC 的 TypeScript worker 提供程序执行隔离和资源控制，但不能仅凭 worker-thread 推断其具备 OS 级文件、网络或进程沙箱能力。通过当前 SDK 绑定调用工具，并遵守工具权限、审批和 sandbox 策略；不要通过程序直接访问 Node API 或子进程来绕过宿主工具边界。
## 11. 计划与子智能体

### 何时写计划

多阶段、多模块、依赖关系复杂、风险较高、需要长时间执行或跨会话续跑时，先写可验证计划。简单任务直接执行，不为形式写计划。

计划至少包含：

- 目标和不做什么。
- 相关文件/模块。
- 依赖顺序。
- 每步执行工具。
- 写入边界。
- 验收命令和成功条件。
- 失败时的回滚/降级路径。

### 何时委派

只在独立工作能抵消代理启动和协调成本时委派。优先委派只读调研、正交审查和文件边界明确的独立实现；不按“跨两个模块”机械触发。

每个子智能体 prompt 必须自包含：

```text
TASK:
一个原子目标。

WORKING_DIR:
绝对工作目录。

EXPECTED OUTCOME:
具体交付物和验收标准。

REQUIRED TOOLS:
当前环境确实可用的工具。

MUST DO:
必要检查和分析。

MUST NOT DO:
禁止操作、禁止修改范围。

CONTEXT:
文件路径、项目现有模式、已知约束。

ACCEPTANCE:
明确的测试/检查命令及通过标准。

REPORT:
修改文件、关键结论、实际验证、未解决问题。
```

子代理无声失败是可能情况。回收结果后，主代理检查任务状态、文件 diff 和验证证据；不得仅凭子代理的成功声明验收。

## 12. 写操作安全与恢复

| 风险 | 示例 | 要求 |
|---|---|---|
| 只读 | 搜索、读取、状态检查 | 直接执行 |
| 低风险写入 | 单文件局部修改 | 精确编辑并复核 diff |
| 批量写入 | 跨文件替换、生成文件 | dry-run、命中范围检查、验证残留 |
| 高风险写入 | 删除、覆盖、远程提交、生产操作 | 检查授权、目标、备份/回滚路径；超出用户授权时先询问 |

通用规则：

- 修改前检查 git status 和现有 diff，不覆盖用户未提交工作。
- 只改任务要求的最小范围。
- 批量改写保留编码、行尾和文件权限。
- 非幂等操作失败后先查状态，不盲目重跑。
- 不吞异常；区分工具故障、输入错误、权限错误、业务失败和部分成功。
- 远程写入必须验证最终远端状态。
- 任何未运行的测试都不能报告为通过。

## 13. 验证闭环

按风险选择验证深度：

1. 范围：修改文件与命中数量正确。
2. 内容：diff 与需求一致，无意外改动。
3. 结构：AST/格式/类型检查通过。
4. 行为：相关单元测试或集成测试通过。
5. 系统：必要时运行构建或端到端检查。

失败时：

- 保留已知成功结果。
- 缩小失败范围。
- 查明根因后再重试。
- 降级工具时重新检查输出语义。
- 验证未通过时明确报告阻塞，不得宣称任务完成。

## 14. 红旗

发现以下任一情况，停止并重新选择路径：

- 已知文件仍全文扫描整个仓库。
- 多文件读取被拆成多次单文件调用。
- FastCtx 文件工具可用却用 shell 读取本地文件。
- AST 结构改写使用宽泛正则。
- 用全文搜索代替调用链/影响面分析。
- 未检查工具 schema 就调用想象中的工具。
- 把 GitHub / Context7 插件当成默认依赖。
- 无依赖且收益明确的调用被串行执行。
- 批量请求已可合并却重复往返。
- 并行执行者写入同一文件。
- 简单机械任务被委派给子智能体。
- 非幂等操作失败后盲目重试。
- 未验证就报告成功。


## 15. CLI、编程规范与工程原则

本技能不仅负责选择工具，也负责约束工具执行方式和代码交付质量。详细内容按任务类型按需读取，不必每次加载所有参考文档：

| 任务 | 参考文档 |

| 架构取舍、工程定律、复杂性和性能决策 | [ENGINEERING-PRINCIPLES.md](references/ENGINEERING-PRINCIPLES.md) |

### 编程执行底线

- 动手前先检查需求、现有实现、项目约定和触发技能；不在信息不足时猜测架构。
- 优先项目原生 API、现代语言 API、现有依赖和成熟抽象；不为“现代化”而无收益地升级。
- 优先小函数、清晰命名、单一抽象层级、早返回；避免深嵌套和魔法值。
- 不吞异常；在输入边界和契约边界校验；资源确定性释放。
- 默认不可变、纯函数和组合；仅在确有收益时引入可变状态、继承或复杂抽象。
- 先测量瓶颈，再优化；性能优化不得破坏正确性、可读性和可维护性。
- 保持幂等性，明确异步/并发语义、取消、超时和共享状态。
- 不过度防御：边界处严谨，内部可信契约不重复堆叠无意义检查。

### 具体实现的速度与内存优先规则

- 正确性、安全、数据完整性和既有 API 契约是硬约束；满足硬约束后，默认优先选择更快且峰值内存更低的具体实现。
- 先推导时间/空间复杂度和当前计算模型下可达到的理论下界；选择对真实 workload 渐近复杂度最优或接近下界的算法。
- 不能只看 Big-O：同时考虑常数因子、缓存局部性、数据布局、分配/拷贝、GC、分支、IO 和网络往返。
- 主动 benchmark + profile/trace + heap/allocation 分析，围绕真实热点反复优化；每轮都要回归测试，并复测时间和峰值内存。
- 大数据优先流式、分块、有界队列和紧凑表示；减少无效物化、重复缓冲区、临时对象和数据复制。
- 用户明确要求性能优先时，不以“过早优化”为由跳过性能设计和测量；允许热点使用低层优化，但要隔离、说明并证明收益。
- 对“理论最快最省”给出模型、假设和下界；无法形式证明时，报告当前环境与 workload 下测得的最佳结果，不作绝对保证。

### 工程原则使用规则

- KISS / YAGNI：先实现最小可运行方案，再按真实需求演化。
- DRY：只抽取稳定且真正重复的知识，不为消除几行重复制造耦合。
- SOLID / 高内聚低耦合：用于划分职责和依赖，不要求每个函数都创建接口。
- 面向接口、组合优于继承：在需要替换、测试或隔离变化时使用。
- 单一事实来源 / CQRS：避免重复权威状态；读写职责明显分离时再应用。
- 最小惊讶 / 约定优于配置：默认行为可预测，例外必须显式记录。
- Gall、Worse is Better、第二系统效应：渐进演化，警惕一次性过度设计。
- Hyrum 定律：公开行为要考虑兼容性，尤其是已有调用方依赖的边界。
- 阿姆达尔定律：先确定总耗时中的瓶颈占比，再决定优化重点。
- 复杂性守恒 / 抽象漏洞：说明复杂度被转移到实现、调用方、配置还是运维；抽象不能替代底层理解。
- 第一性原理 / 奥卡姆 / Pareto：先找关键约束，只保留能显著改善结果的实体和工作。
- 破窗 / 墨菲 / 防御性编程：修复已知坏味道，在真正的失败边界设置保护，不在所有地方堆防御代码。

以上原则是决策工具，不是机械检查项。原则冲突时以用户目标、已存在契约、风险和可验证证据为准。

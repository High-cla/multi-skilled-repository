# 编程规则与代码质量约定

本规范适用于实现新功能、修复 bug、重构和代码审查。目标是让代码足够简单、明确、可测试、可维护，并符合项目现有风格。

## 1. 动手前

1. 明确用户目标、成功条件和不做范围。
2. 读取项目入口、相关模块、依赖、测试和现有实现。
3. 搜索已有 API/工具/抽象，优先复用项目原生能力。
4. 检查触发技能：clean-code、coding-standards、systematic-debugging、writing-plans、test-driven-development 等。
5. 先判断修改是文本、语法结构、符号关系还是语义问题，分别选 rg、sg、codebase-memory 或直接阅读。
6. 不在事实不足时猜测架构；但简单任务不要被不必要的计划阻塞。

## 2. 代码设计原则

### 简单、聚焦、可组合

- 小函数，单一职责，一个函数尽量只表达一个意图。
- 单一抽象层级；不要在同一个函数里混合业务决策、协议细节和资源管理。
- 命名表达意图，避免缩写、含糊动词和过度泛化名称。
- 早返回，减少深层 if/else、嵌套循环和布尔分支组合。
- 组合优于继承；优先小而清晰的函数和对象组合。
- 面向接口编程，但不要为每个函数/类都强行创建接口。
- 遵循最少知识原则（LoD）：模块只依赖完成工作必需的直接协作者。
- 依赖抽象而非具体实现；抽象必须有真实变化点、测试隔离点或复用收益。

### 类型、接口与契约

- 类型表达业务约束，避免过宽的 any/unknown 泄漏。
- 在外部输入、文件、网络、用户数据和跨模块边界进行验证。
- 明确前置条件、后置条件、不变量和错误语义。
- 输入宽容只适用于协议明确允许的兼容差异；输出应符合契约且保持规范。
- 公共 API 的可观察行为需要兼容性意识；改变前检查调用方和测试。
- 避免隐式副作用；状态修改、IO 和依赖注入应清楚可见。

### 不可变、纯函数和现代 API

- 默认不可变；只在明确需要状态变化时使用可变数据。
- 优先纯函数，将 IO 放在边界，将业务计算留在可测试逻辑中。
- 优先使用语言/平台现代原生 API、迭代器、集合操作、结构化并发和高效数据结构。
- 使用现代 API 前先确认项目运行时版本和兼容范围。
- 不为使用新语法而牺牲团队可读性、兼容性或调试能力。
- 避免重复转换、无意义拷贝和不必要的中间数组；对大数据优先流式处理。

### 错误、资源与安全

- 错误不能吞噬；保留 cause、上下文和可操作信息。
- 只在系统边界、外部输入和契约边界做必要校验；可信内部契约不要重复堆叠防御。
- 不用空 catch、默认值或静默回退掩盖异常。
- 文件、流、连接、锁、事务等资源必须确定性释放。
- 明确 timeout、取消、重试、幂等键和部分成功语义。
- 不记录密钥、token、个人敏感信息和不必要的原始载荷。
- 最小化权限和数据暴露；拼接 shell、SQL、路径或 URL 时使用正确的参数化/转义机制。

## 3. 并发与异步

- 区分并发与并行；只有存在独立工作且收益高于协调成本时才并发。
- 明确共享可变状态、竞态、锁粒度、取消传播和超时。
- 对同一资源的写操作串行化，或使用明确的锁/版本/乐观并发控制。
- 任务应尽可能幂等；对非幂等操作使用状态检查、幂等键或去重机制。
- 限制并发度，避免无限 Promise.all、无界队列和资源耗尽。
- Promise.all 用于独立且允许并发的任务；有数据依赖的步骤必须 await 分层执行。
- 部分失败时保留成功信息，不把整体失败误报成全部失败或全部回滚。

## 4. 性能与内存优先：以理论最优为目标

具体代码实现默认将**运行速度和内存占用**作为首要优化目标。在正确性、安全、数据完整性、公开契约和兼容性这些硬约束满足后，优先选择运行更快、峰值内存更低的实现；不能仅为了表面上的简洁或可读性，接受明显且可避免的性能损失。热点中的低层优化可以采用，但必须隔离复杂度、说明意图并用测试锁定行为。

### 4.1 先定义性能目标与理论下界

- 明确 workload：输入规模、分布、冷热状态、并发度、数据生命周期、运行时/硬件和资源限制。
- 明确优化指标：端到端延迟、吞吐量、CPU 时间、分配次数/字节数、峰值 RSS/堆内存、GC 暂停、IO/网络往返；按任务选择主要指标。
- 分析算法时间复杂度和空间复杂度，估算不可避免的工作量与资源下界（例如必须读取的输入字节数、必须产生的输出量、比较模型下的排序下界、必须保留的状态）。
- 优先选择在目标 workload 与约束下达到已知渐近下界或接近下界的算法/数据结构；若理论下界无法达到，说明瓶颈、假设和差距。
- 理论复杂度不是实测速度的替代品：常数因子、缓存局部性、分支预测、内存带宽、分配器和 IO 都会改变实际结果。

### 4.2 算法与数据结构

- 优先消除不必要的工作：重复扫描、重复计算、无效转换、重复解析、冗余排序、无谓同步和多余网络往返。
- 按实际查询/更新模式选择数据结构；比较哈希、排序数组、树、位图、紧凑数组、索引和专用结构的时间/空间成本。
- 热路径避免不必要的动态分派、装箱/拆箱、对象创建、闭包捕获和临时集合；使用预分配、紧凑表示或批量操作前，先验证容量与生命周期。
- 在适用语言和运行时中评估原生批量 API、向量化/SIMD、并行算法和编译器优化；不得猜测 API 可用性或把理论并行度当作实际加速。
- 不要只优化局部复杂度：以端到端关键路径和真实调用频率判断收益。

### 4.3 内存优先约束

- 同时关注总分配量、峰值活跃内存、对象数量、堆外内存和生命周期；不能只看进程退出后的内存。
- 大数据优先流式、分块、增量处理、背压和有界队列，避免无界缓存或一次性物化完整数据集。
- 减少重复缓冲区、字符串拼接、序列化往返和中间数组；能安全地原地处理、复用缓冲区或传递视图时，优先评估这些方式。
- 对零拷贝、内存映射、对象池和复用缓冲区，必须审查所有权、别名、并发、生命周期、碎片和释放时机；不安全的“省内存”不是优化。
- 以数据量上界推导空间复杂度；峰值内存必须在最大/压力输入下测量，不能只用小样本推断。
- 若速度与内存存在冲突，明确绘制/比较时间—空间取舍；在用户未指定额外偏好时，优先选择同时降低二者的 Pareto 改进，不存在双赢时以更严格的资源约束和真实 workload 决定。

### 4.4 基准测试、剖析与迭代调优

1. 建立未优化基线；用代表性输入和相同环境重复 benchmark，必要时预热并隔离噪声。
2. 使用 profiler、trace、火焰图、分配分析或 heap profile，定位 CPU 热点、阻塞点、对象分配和内存峰值。
3. 每轮只针对主要瓶颈改动，先提出可验证的性能假设，再实现。
4. 对比优化前后结果：至少记录同口径延迟/吞吐量和峰值内存；关注 p50/p95/p99、GC、CPU、IO 等适用指标。
5. 对噪声、JIT、缓存、后台负载、数据分布和冷启动进行控制；明显差异需要重复验证，不能拿一次跑分下结论。
6. 每轮运行正确性、边界、并发和回归测试；性能提升不得依赖错误结果、未定义行为或数据丢失。
7. 持续迭代到已知理论下界、硬件/IO 下界、资源预算或可测改进空间已逼近；当收益低于测量噪声或代价超过收益时停止，并记录剩余瓶颈。

### 4.5 优化验收规则

- 优化前后使用同一数据集、环境、参数和测量口径；记录 commit、命令、数据规模、运行次数和结果。
- 优化结果必须同时报告速度变化、内存变化和正确性验证；只加速但导致不可接受的峰值内存增长，不算完成。
- 对高频热点允许采用更低层、非直观但更快的实现；将其限制在局部，并解释不变量、数据布局和测量收益。
- 不声称“绝对理论最快/最省”。只有在明确计算模型、输入约束和假设下证明达到下界，才可称为该模型下最优；其余表述为“当前约束与 workload 下测得的最佳方案”。
- 避免没有基准依据的微优化；但一旦用户明确要求性能优先，就必须主动建立基准、分析下界、剖析热点并迭代，而不是以“过早优化”为由跳过性能工作。

## 5. 测试与重构

- 先明确可观察行为和验收条件。
- Bug 修复优先添加能复现问题的测试。
- 适用时采用 RED → GREEN → REFACTOR；先确认测试失败确实对应目标问题。
- 测试边界、异常、空值、并发、幂等和回归行为。
- 重构不应无意改变海勒姆行为；若改变行为，明确这是修复还是破坏性变更。
- 完成后运行最相关的测试、类型检查、lint、构建；没有运行的检查不得报告通过。
- 保持 diff 聚焦，不顺手进行无关格式化和大范围重命名。

## 6. 常见代码坏味道

- 魔法数字/字符串：提取有意义的常量或枚举。
- 复制粘贴逻辑：抽取稳定的共同知识，不制造过度抽象。
- 巨型函数/类：按职责和变化原因拆分。
- 深层嵌套：早返回、卫语句、拆分函数。
- 多层透传：减少不必要包装，直接表达依赖。
- 吞异常/宽泛 catch：按可恢复性分类并保留错误上下文。
- 过度防御：删除重复校验，保留真正的边界检查。
- 过度设计：删除未被需求支持的扩展点、配置项和抽象层。

## 8. 常用原则速记（显式定义）

| 原则 | 全称/含义 | 实际执行 |
|---|---|---|
| KISS | Keep It Simple, Stupid：保持简单 | 在满足需求和约束的方案中选择概念最少、路径最直接的实现 |
| YAGNI | You Aren't Gonna Need It：不要实现尚未需要的功能 | 不预建未被当前需求、调用方或验收标准支持的扩展点 |
| DRY | Don't Repeat Yourself：不要重复表达同一知识 | 对稳定的业务规则建立单一权威定义；仅偶然相似的代码不强行抽象 |
| SOLID | 五项面向对象设计原则 | 用于控制职责、扩展、替换、接口和依赖方向，不要求每个模块机械套类结构 |
| LoD | Law of Demeter：最少知识原则 | 只依赖直接协作者，避免穿透对象内部层级访问远端细节 |

### SOLID 五项

1. **S — Single Responsibility Principle（单一职责原则）**：模块应围绕一个主要变化原因组织；不要把无关职责塞进一个类/模块。
2. **O — Open/Closed Principle（开闭原则）**：稳定模块应能在尽量少修改原有正确代码的情况下扩展；仅在变化模式真实存在时引入扩展点。
3. **L — Liskov Substitution Principle（里氏替换原则）**：子类型/替代实现必须遵守基类型契约，不能强化前置条件、削弱后置条件或改变关键不变量。
4. **I — Interface Segregation Principle（接口隔离原则）**：调用方不应依赖自己不用的方法；按调用方需求拆分接口，避免臃肿通用接口。
5. **D — Dependency Inversion Principle（依赖倒置原则）**：高层策略与底层细节依赖稳定抽象；抽象应由业务需求驱动，不为单一实现制造无价值接口。

原则应用顺序：先确定职责和契约，再检查是否存在稳定扩展点、可替换实现和接口污染。优先用函数组合和模块边界解决问题；不要为了“满足 SOLID”而增加没有实际用途的类、工厂、容器或抽象层。

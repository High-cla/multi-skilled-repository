# DSH 执行效率操作手册

本手册补充 `cli-first-decision` 的端到端执行策略。目标不是最大化并行数或压缩单次工具调用，而是在正确性、安全性和可恢复性不退化的前提下，缩短关键路径、减少不必要往返，并控制模型上下文与进程资源。

## 1. 先做低成本侦察，再决定执行形态

1. 确认当前会话真实可见的工具、参数 schema、权限和副作用；PTC 模式先读取当前 `tools:sdk` 与 runtime instructions。
2. 先读取任务入口和必要元数据：项目说明、manifest/lockfile、相关配置、测试入口、Git 状态。已知路径批量读取；未知范围先用 `glob` / `grep` / `rg` 缩小。
3. 将任务拆成依赖 DAG，标注每一步的输入、输出、耗时类别、Read/Write 集合和失败后果。
4. 先执行低成本且能解除最多依赖的步骤。不要为了“先并行”而启动尚无明确输入或验收标准的工作。

## 2. 并行策略：先看安全分类，再看收益

### 可并行的条件

- 调用之间没有数据或状态依赖。
- 对当前工具和当前参数，DSH 调度策略明确给出 concurrency-safe/parallel。
- 不会并发写入同一文件、记录、远程资源或共享状态。
- 启动、协调、限流和结果整理成本低于节省的关键路径时间。

PTC 的 `Promise.all` 只表达程序希望并发发起调用，不是实际并行保证。只有当前参数被策略明确判为 concurrency-safe 才允许重叠；未知、未声明、非法或检查异常按 exclusive 处理。exclusive 调用会形成串行屏障。

### 扇出与部分失败

- 使用当前 runtime 的 `maxParallelSubCalls` 和工具服务的真实限额；不要把某个版本文档中的默认值写成永久常量。
- 若任何一个分支失败仍需要其他分支的结果，用 `Promise.allSettled` 或逐项 `try/catch`。普通 `Promise.all` 的任一 reject 会使聚合 Promise reject。
- 将结果按原任务/路径标识关联，不依赖 Promise 完成先后推断业务顺序。
- 不要对同一资源做并发写入。把只读预检与写入阶段分开；共享资源写入按顺序执行。

## 3. 长任务：后台运行并完成生命周期管理

FastCtx 前台 `run` 有四分钟上限。预计超过该上限的命令使用 `run_background`，记录其返回的 `job_id`。

推荐生命周期：

1. 启动后台任务，保存原样返回的 job id。
2. 利用主流程处理与该任务无依赖的工作；不要空等，也不要用紧密循环持续轮询。
3. 通过 `job_list` 找回作业状态，通过 `job_output` 查看新增输出/终态结果。
4. 结合状态、退出结果和日志确认成功；输出被窗口化或标为 Partial 时，按返回信息读取完整日志/续读数据。
5. 只有在确认 job id 和取消理由后才用 `job_kill`。不要因暂时没有新输出就认定任务卡死或擅自终止。

后台任务可能在前台会话结束后继续存在。主流程结束不等于后台进程已经停止；最终汇报前必须确认作业状态，并说明仍在运行的任务。

## 4. CLI 批处理与管道：减少往返，不制造语义损失

- 同一来源、同一 API 且支持批量请求时，一次批量调用通常优于多次独立调用。
- 数据可通过 stdin/stdout 直接传递时使用管道，避免写临时文件或反复读取。
- Bash 多段管道需要传播任一阶段失败时，显式使用 `set -o pipefail`；默认 pipeline 状态可能只反映最后一个命令。
- 对 JSON/JSONL 使用结构化解析。多个顶层 JSON 值/JSONL 可用 `jq -n 'inputs | ...'`；不要为图方便对大输入使用 `--slurp` 全量物化。
- 路径可能包含空格或换行时使用 NUL 分隔（如 `fd -0 | xargs -0`），避免命令替换和不安全字符串拼接。
- 先检查项目已有脚本/justfile 和 CLI 是否安装；不要为了单次任务静默引入依赖。

示意：

~~~bash
set -o pipefail
fd -0 -e ts src | xargs -0 -r rg -n 'TargetSymbol'
~~~

## 5. 渐进式上下文：只把决策所需信息交给模型

按以下顺序缩小读取范围：

1. **发现**：列出候选文件和元数据，不急于读取全文。
2. **定位**：用关键词、符号索引或 AST 找到相关定义/调用点。
3. **定点读取**：只读取命中行附近的范围；若工具返回 Partial，严格使用其续读参数。
4. **程序内归纳**：PTC 中间值保留在执行环境，先筛选、投影、去重和聚合。
5. **最小返回**：只返回路径、行号、状态、关键字段、短摘录和必要错误。

注意：PTC 子调用结果通常不会全部重新进入模型 transcript，但图像和 `additionalContexts` 可被 dispatcher 独立转发。它们也消耗上下文预算，不能只按外层 `return` 大小估算。

## 6. 结果复用与缓存失效

- 优先复用当前任务中已取得且仍然有效的读取结果，不要重复扫描相同文件或重复请求相同元数据。
- 不假设存在通用的 `ctx.memory`、缓存 API 或跨会话状态；只有当前会话 schema/运行时文档明确提供时才能使用。
- 如确需建立持久缓存，缓存键至少覆盖仓库/ref、相关文件内容或版本、配置和工具版本；更新分支、修改文件、切换版本或变更配置后必须失效/重建。
- 对时效性外部数据、权限状态和可变远端资源，不复用未经重新验证的旧结果。
- 缓存只是性能优化，不得成为正确性或审计的唯一依据；需要时提供禁用缓存的路径。

## 7. 子智能体：只委派足够独立且足够大的工作

满足以下条件再委派：任务边界清楚、上下文可自包含、Read/Write 范围可分离，且并行节省大于启动与协调成本。

委派说明应包含原子目标、绝对工作目录、允许/禁止修改范围、已知约束、交付格式和验收条件。多个执行者不得同时写同一文件或共享接口；优先让子智能体只读分析并提交文件/符号级发现，由主流程统一决策和写入。

回收后重新检查任务状态、diff、测试和外部副作用。子智能体声明“完成”不是验收证据。

## 8. 失败恢复与安全边界

1. 保留成功分支结果，明确失败分支和错误类型（输入、权限、限流、超时、工具故障或业务失败）。
2. 对可重试的瞬时错误设置有限重试和退避；对参数错误、权限拒绝和业务失败先修正原因。
3. 对写入、发布、删除和其他非幂等调用，失败后先检查远端/本地实际状态；不盲目重放。
4. 对运行中的后台任务核对 job id 和状态；只有确认取消安全且必要时才终止。
5. 工具调用成功不等于业务成功。必须核验最终状态、退出码、变更范围和验收条件。

## 9. 不要把项目级构建技巧误用为通用 DSH 规则

pnpm 安装加速、Actions 缓存、构建缓存、HMR/文件监听和 watcher 自动重启，都是具体项目/工具链的优化，不是每个 DSH skill 或仓库都适用的默认配置。

只有在任务确实涉及对应项目的构建/发布流程时，才检查其 package manager、lockfile、CI workflow、运行时和已有缓存；先测量冷/热构建与安装耗时，再决定是否调整。不要仅为优化一个技能文档新增 pnpm 依赖、CI workflow、nodemon/chokidar 或未经项目验证的配置。安装脚本白名单、安全设置和缓存权限必须按项目实际包管理器版本核验。

## 10. 最终检查

- [ ] 调用分组符合数据依赖 DAG。
- [ ] 所有并发调用均有明确安全分类，且未超过当前运行时限额。
- [ ] 同源批量请求和可合并管道已优先考虑。
- [ ] 后台任务有可追踪 job id，并已检查终态/退出结果。
- [ ] PTC 中间结果已筛选，返回值和附加上下文均纳入预算。
- [ ] 缓存输入、版本和失效条件明确；没有臆造缓存 API。
- [ ] 写入边界互斥，非幂等失败已核实实际状态。
- [ ] 测试、diff 和最终验收都有真实证据。

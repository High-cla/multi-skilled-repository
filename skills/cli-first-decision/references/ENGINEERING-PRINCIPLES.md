# 工程原则、定律与设计取舍

原则用于帮助判断，不是互相独立的硬规则。遇到冲突时，以用户目标、既有契约、风险、可验证证据和整体成本为准。

## 1. 系统演化与复杂性

### Gall 定律

复杂系统通常从简单且有效的系统演化而来。先建立可运行的最小系统，再依据真实反馈迭代；不要一开始设计覆盖所有未来场景的完整架构。

**实践**：先实现端到端最小路径，保留清晰边界和可演进点；不要预埋没有需求支撑的插件化/配置化层。

### Worse is Better

简单、可理解、可部署、可传播的实现，常常优于理论上更完整但复杂难用的设计。

**实践**：先选能够正确解决当前问题的简单方案；复杂性只有在带来可测量收益时才值得引入。简单不等于忽略安全、正确性和必要边界。

### 第二系统效应

第一个系统成功后，容易在第二个系统中堆积所有“以后可能用”的能力。

**实践**：逐项要求新抽象、配置和扩展点说明当前需求、调用方和验收收益；不能说明的先不做。

### 复杂性守恒定律

固有复杂度不会凭空消失，只会转移给实现、调用方、配置、运维或用户。

**实践**：做架构决策时记录复杂度被放到哪里、由谁承担、如何诊断和维护；不要把复杂 wrapper 当作复杂度已消失。

### 阿姆达尔定律

整体性能提升受可优化部分在总耗时中占比限制。

**实践**：先 profile 并定位瓶颈，再优化关键路径；不要只优化显眼但占比很小的局部。

### 时间与空间最优化

对具体代码实现，默认将速度和内存占用作为首要优化目标；在正确性、安全和既有契约这些硬约束内，追求更低端到端耗时、更高吞吐和更低峰值内存。

**实践**：
- 先确定 workload、时间/空间复杂度和已知理论下界，区分不可避免的成本与实现浪费。
- 通过 benchmark、profiler、trace 和内存分析定位真实热点；按相同条件反复测量，避免凭感觉或单次跑分优化。
- 优先减少算法工作量、IO/网络往返、数据拷贝、对象分配和无界缓存；大数据使用流式/分块/有界处理。
- 允许热点采用低层、紧凑、硬件友好的实现，但必须验证正确性、生命周期和并发安全，并隔离复杂度。
- 若时间与空间不可同时最优，明确 trade-off；不声称不带计算模型和假设的“绝对最快/最省”，以当前约束下可测、可复现的 Pareto 最优为目标。

### 抽象漏洞定律（Leaky Abstractions）

非平凡抽象会暴露底层细节，无法彻底消除底层机制的影响。

**实践**：抽象应降低常见操作成本，同时文档说明关键失败模式；涉及文件系统、网络、并发、事务或权限时，仍需理解底层语义。

## 2. API、兼容性和边界

### 海勒姆定律（Hyrum's Law）

当调用方足够多时，所有可观察行为都可能被依赖，包括未文档化行为和 bug。

**实践**：改公共 API 前搜索真实调用方、测试和序列化结果；优先兼容性演进，破坏性变更必须显式说明、迁移并测试。

### 健壮性原则

传统表述是“接受时宽容，发送时严格”，但不能把宽容理解为吞掉错误或接受任意畸形输入。

**实践**：对协议明确允许的兼容差异做容错；对输出严格遵循规范；对非法状态给出明确错误，避免静默修复掩盖数据问题。

### 最小惊讶原则

API 和系统行为应符合使用者合理预期。

**实践**：命名、默认值、错误、排序、重试和副作用保持一致；有意外行为时文档说明，并避免隐式改变状态。

### 约定优于配置

合理的统一默认值可以减少配置负担，但约定应可发现、可覆盖且不产生隐式惊讶。

**实践**：默认值覆盖常见场景；仅对真实差异开放配置；避免为了潜在未来需求暴露大量开关。

### 单一事实来源（SSOT）

同一权威状态或定义应只有一个事实来源，其他位置引用或派生。

**实践**：避免重复维护 schema、版本、业务常量和配置；生成物标明来源并可重建。

## 3. 设计和模块化

### 高内聚低耦合

模块内部围绕同一职责协作，模块之间依赖少且稳定。

**实践**：按业务能力和变化原因划分模块；减少跨模块共享可变状态；让依赖方向清楚。

### 面向接口编程

调用方依赖稳定契约，而不是不必要地绑定具体实现。

**实践**：在存在替换、测试隔离或多实现需求时定义接口；避免为简单函数和单一实现创建空洞抽象。

### 命令-查询分离（CQRS）

改变状态的操作与读取数据的操作尽量分开。

**实践**：写操作清楚表达副作用；查询尽量无副作用。只有读写模型确实存在不同扩展需求时，才引入复杂 CQRS 架构。

### 关注点分离、组合优于继承、最少知识原则

职责、变化原因和依赖边界应明确；优先组合可替换组件；模块只知道直接协作者完成当前职责所需的信息。

**实践**：避免深继承、跨层穿透和上帝对象；不要为理论纯洁性制造过多接口和转发层。

## 4. 风险与可靠性

### 防御性编程 / 墨菲定律

预设外部依赖、输入、网络、进程和并发可能失败，但保护要放在真正的风险边界。

**实践**：检查用户输入、权限、文件存在性、网络响应、资源生命周期和共享状态；内部可信契约不重复堆叠相同校验。

### 破窗理论

已知坏味道长期不修会降低团队对质量的标准。

**实践**：修复任务附近明确发现的严重问题；不借机对无关模块做大规模格式化或重构。

### 第一性原理

从目标、约束、成本和系统真实机制出发，而不是照搬既有做法。

**实践**：先问要解决的根问题和不可变约束，再选工具/架构；已有方案只有在符合约束时才复用。

## 5. 最小化、最大化和取舍

### 奥卡姆剃刀

没有必要时不增加实体、层次和假设。

**实践**：在效果相当时选择组件少、依赖少、路径短的方案；不能以删掉必要安全边界为代价。

### Pareto 原则

少量关键因素往往贡献大部分结果。

**实践**：优先解决高频路径、最大瓶颈和最大风险；先覆盖最重要的 20%，再根据数据决定扩展。

### 最小化

- 实现代码和概念数量。
- 可变状态与共享状态。
- 模块耦合、依赖和权限。
- API 面积、配置项和重复逻辑。
- 工具调用、上下文和不必要读取。

### 最大化

- 内聚、可测试性和自动化。
- 契约清晰度和行为一致性。
- 可观测性、可恢复性和幂等性。
- 可替换性、可演进性和部署可靠性。

最小化/最大化不是绝对指标：减少代码不能牺牲清晰度；最大化抽象也可能导致过度设计。

## 6. 常见原则冲突的处理

| 冲突 | 决策方式 |
|---|---|
| DRY vs KISS | 只有共同知识稳定时才抽取；否则保留小段重复 |
| 抽象 vs YAGNI | 有真实变化点/测试收益才抽象 |
| 性能 vs 可读性 | 用户要求性能优先时，不能以表面简洁为由牺牲可测的速度/内存收益；隔离并测试低层复杂度 |
| 速度 vs 内存 | 比较峰值内存与端到端耗时，优先 Pareto 改进；冲突时遵循资源硬约束 |
| 健壮性 vs Fail Fast | 外部边界容错，内部契约快速暴露错误 |
| 约定 vs 显式配置 | 常见路径给默认值，重要差异显式配置 |
| 并行 vs 简单性 | 关键路径收益超过协调/冲突成本才并行 |
| 兼容性 vs 修复 bug | 明确可观察行为、影响面和迁移策略 |
| 模块隔离 vs 调用效率 | 避免无意义网络/抽象边界，按真实变化和故障域划分 |

## 7. 架构决策记录（ADR）触发条件

满足任一条件时，记录简短 ADR：

- 影响多个模块或公共 API。
- 引入持久化、队列、缓存、并发模型或新依赖。
- 改变权限、安全边界、部署方式或数据模型。
- 在多个长期代价不同的方案之间做选择。

ADR 至少包含：背景/约束、候选方案、选择及理由、代价/风险、回滚/迁移和验证方式。单文件小改不需要 ADR。

# 从零开始的架构选择与设计流程

本指南适用于全新项目、系统重建和重大架构重设计。目标不是选择“最先进”或“最流行”的架构，而是在明确约束下，先确定可验证、适合当前 workload 的最佳架构，再进入主体实现。

**性能/内存优先**：速度、吞吐和峰值内存是核心架构质量属性，不应等到功能完成后才补救。正确性、安全、数据完整性和明确的合规要求是硬约束；在满足这些约束后，优先选择端到端延迟更低、吞吐更高、峰值内存更低的方案。

## 1. 先判断是不是绿地项目

- **真正从零开始**：先做架构设计，不得直接创建一堆文件、安装框架后再倒推架构。
- **已有代码库**：先读取现有架构、模块边界、数据流、依赖、构建/部署方式和测试；先测量现状，避免无依据地推倒重来。
- **系统重建/重大重构**：明确哪些既有 API、数据格式、用户行为和外部集成必须兼容；区分必须保留的约束和可以重新选择的实现。

## 2. 建立架构输入：需求与质量属性

先写一页以内的项目约束摘要，不清楚的项标为假设，不要伪装成确定事实。

### 2.1 功能边界

- 目标用户、核心场景、关键用户旅程和不做范围。
- 输入/输出、外部系统、集成协议和数据所有权。
- 核心业务不变量、事务边界、权限和审计要求。
- 首个可交付纵向切片（vertical slice）。

### 2.2 非功能与运行约束

按项目选择并量化：

| 维度 | 需要明确的输入 |
|---|---|
| 性能 | p50/p95/p99 延迟、吞吐量、并发数、冷启动、批处理窗口 |
| 内存/资源 | 峰值 RSS/堆内存、单实例预算、分配/GC、CPU、IO、网络预算 |
| 工作负载 | 请求/事件分布、读写比例、数据量/增长率、热点/突发、批量大小 |
| 数据 | 一致性、事务、排序、去重、保留期、备份、迁移和数据驻留 |
| 可靠性 | 可用性目标、故障域、RTO/RPO、降级/恢复策略 |
| 安全 | 身份、授权、密钥、威胁模型、隐私和合规边界 |
| 演进 | 预计变化、团队边界、扩展/替换需求、兼容要求 |
| 交付/运维 | 团队人数与技能、部署环境、CI/CD、监控、值班和运维能力 |
| 经济性 | 开发周期、基础设施/托管成本、流量与数据增长成本 |

**没有数字时如何处理**：先向用户询问会改变架构选择的关键缺失约束；其余项使用明确标注的保守假设，给出可逆的初始架构与验证计划。不要捏造容量目标。

## 3. 必须做网络官方文档调研

从零开始或重大架构决策时，必须查阅当前可用的网络资料。不能只凭模型记忆、个人偏好或陈旧博客决定技术栈。

### 3.1 调研范围

根据候选技术栈逐项查阅：

- 语言、编译器、运行时、GC、线程/异步执行模型和版本支持。
- 框架的架构指南、生命周期、扩展模型、性能建议和兼容矩阵。
- 数据库/存储/索引的事务、一致性、查询模型、容量、备份和性能文档。
- 消息队列、缓存、RPC/HTTP、序列化、流处理的交付语义、延迟和资源限制。
- OS、容器、云服务、部署平台、网络、观测、安全和权限边界。
- 官方参考架构、Well-Architected 指南、迁移/扩展/故障恢复指南。
- 相关标准、协议规范、RFC、语言规范和安全公告。

### 3.2 来源优先级

1. **规范/标准与官方 API 文档**：语言规范、RFC、项目/厂商官方文档、版本与兼容说明。
2. **官方架构资料**：Well-Architected Framework、Architecture Center、官方 reference architecture、性能/可靠性/安全指南。
3. **可复现的独立资料**：有代码、环境、样本和方法论的基准、技术报告、论文或维护良好的工程文档。
4. **社区文章/讨论**：用于发现问题和反例，不单独作为关键架构结论的证据。

只使用与目标版本匹配的文档。检查发布日期/最后更新、弃用状态、兼容矩阵和迁移说明；不能把最新版文档的 API 假定为项目锁定版本可用。

### 3.3 网络搜索与资料核验

- 用 Web/Search/浏览器搜索具体技术名称 + architecture/design/performance/memory/limits/consistency/security/production 等问题。
- 先找官方域名和官方仓库，再找独立验证资料；对关键结论至少交叉核对一份不同来源，厂商特有能力除外。
- 打开原始文档核验关键段落，不只依赖搜索摘要或 AI 摘要。
- 比较候选技术的限制、默认值、成本、版本差异和已知故障模式；营销性能数字不能替代自己的 workload benchmark。
- 调研记录至少保留：标题、URL、来源类型、文档版本/更新日期、支持的结论、适用前提和仍未知的问题。
- 只记录真正影响本项目决策的证据，不堆砌链接。没有查到的写“未验证”，不能编造出处。
- 若当前环境没有网络搜索能力，尝试当前允许的官方站点访问方式；仍不可用时，明确报告网络调研受阻及影响，不要宣称已完成。

## 4. 形成候选架构，而不是直接押注一种模式

基于约束生成 **2–4 个真正可行的候选方案**。必须包含简单基线，并清楚说明为何更复杂方案值得其额外成本。

| 候选风格 | 适用信号 | 必须计算的代价 |
|---|---|---|
| 模块化单体 / 分层单体 | 领域边界尚在探索、团队集中、需要低延迟和快速交付 | 模块依赖、单体部署/故障域、内部数据边界 |
| 服务化 / 微服务 | 领域边界稳定、团队需要独立发布、不同模块有独立扩缩容/隔离目标 | RPC 网络跳数、序列化、部分失败、一致性、追踪/部署/值班成本 |
| 事件驱动 / 消息队列 | 异步任务、峰值削峰、松耦合和独立消费有明确价值 | 最终一致性、重复/乱序、重试、死信、积压、回压、调试复杂度 |
| Serverless / 托管事件计算 | 负载突发、短生命周期任务、运维负担需要降低 | 冷启动、运行时限制、供应商耦合、计费模型、局部调试 |
| 流处理 / 数据密集架构 | 持续数据流、窗口聚合、吞吐或数据局部性主导 | 状态存储、检查点、背压、恢复、内存状态规模 |
| Edge / 分布式部署 | 数据/用户地域分散，网络延迟或数据驻留是硬约束 | 部署面、同步、冲突解决、安全和运维复杂度 |

模块化单体是**必须评估的基线**，不是所有项目的强制答案。微服务、事件驱动、分布式架构也不是天然更快或更省内存。微服务会引入网络往返、序列化和独立进程开销；只有独立扩缩容、团队自治、故障隔离或部署节奏等收益能够覆盖这些成本时才选用。

## 5. 用硬约束 + 评分矩阵做架构取舍

### 5.1 先设硬门槛

任何候选方案若违反以下任一不可妥协条件，直接淘汰：

- 正确性、数据完整性或事务语义不成立。
- 安全、隐私、合规或权限边界不满足。
- 目标延迟/吞吐/峰值内存无法达到，且没有可行的验证路径。
- 数据规模、可用性、RTO/RPO 或地域约束无法满足。
- 团队没有能力安全地构建、部署、监控和恢复该方案。

### 5.2 再按项目权重评分

使用 1–5 分并记录证据。权重由需求决定，禁止把示例权重当作通用真理。

| 维度 | 性能优先项目必须比较的内容 |
|---|---|
| 端到端性能 | 热路径跳数、算法复杂度、排队、RPC、序列化、锁竞争、p95/p99 |
| 内存/资源 | 进程/服务数量、运行时开销、缓存/队列/副本、峰值工作集、GC |
| 数据与计算局部性 | 热数据是否靠近计算；是否存在重复读写、跨节点 shuffle 和复制 |
| 吞吐与弹性 | 并发模型、批处理、背压、资源上限、扩缩容滞后 |
| 可靠性/安全 | 故障域、隔离、恢复、一致性、最小权限、审计 |
| 开发/运维效率 | 团队认知成本、部署链路、可观测性、调试和故障定位 |
| 生命周期成本 | 开发时间、基础设施、带宽、存储、许可和运维成本 |
| 可演进性 | 模块边界、接口稳定性、数据迁移和渐进替换成本 |

性能与内存是本项目的首要优化目标，但不是绕过正确性、安全和硬资源预算的理由。比较端到端工作负载，而不是局部组件宣传数字。

## 6. 从系统边界向下确定关键设计

架构风格确定后，明确以下决策；不要把它们留给各模块临场各选一套：

1. **系统边界/模块边界**：职责、依赖方向、数据所有权、变更原因和部署单元。
2. **进程与执行模型**：单进程/多进程、线程/异步/Actor/批处理；CPU-bound 与 IO-bound 分开分析。
3. **数据模型与存储**：访问模式、索引、事务、一致性、保留/归档、读写放大和数据布局。
4. **通信**：进程内调用、RPC、HTTP、消息、事件；同步/异步、批量、超时、重试和幂等。
5. **缓存与状态**：缓存层级、失效、内存预算、状态权威来源；不默认增加缓存。
6. **故障与恢复**：故障域、隔离、降级、重放、备份、恢复和演练。
7. **安全边界**：身份、授权、密钥、网络暴露面、数据分类和审计。
8. **部署与观测**：构建/发布、回滚、日志/指标/追踪、告警和容量规划。

### 性能/内存架构检查

- 尽可能让热数据与计算靠近；避免为了“解耦”把高频同步热路径拆成多个网络服务。
- 把 RPC 跳数、序列化/反序列化、跨进程拷贝、数据库往返和同步依赖计入端到端延迟预算。
- 明确每个进程/服务的内存预算，包括运行时、连接池、缓存、队列、请求并发和峰值工作集。
- 明确背压、批量大小、队列上限和最大并发；无界队列会把流量尖峰转换成内存耗尽。
- 选择数据模型、索引和访问路径时，使用真实读写比例、数据规模和查询形状；避免过度通用的抽象损害热路径。
- 缓存、复制、预计算、分片和并行都有成本；必须写出收益假设与失效/一致性策略。
- 任何性能关键架构都应定义负载测试、峰值内存和故障注入验证办法。

## 7. 对高风险假设做原型与架构验证

架构图不是性能证据。以下任一情况需要先做时间盒原型（spike）或可运行的最小垂直切片：

- 两个候选方案在 p95/p99 或峰值内存上差异可能改变选择。
- 数据库、队列、缓存或网络协议的关键能力尚未从目标版本官方文档确认。
- 目标吞吐、尾延迟、数据规模或内存上限没有可信基准。
- 一致性、重试、顺序、背压、故障恢复或安全隔离存在高风险。
- 使用新运行时、编译模式、向量化/GPU/零拷贝或新的部署平台。

原型必须有假设、输入规模、环境、指标和通过阈值。对候选方案使用相同数据与环境；同时测量端到端延迟/吞吐、CPU、峰值内存、分配/GC 和失败恢复。记录结果，而不是只保留“感觉更快”的结论。

## 8. 形成可读的架构表达

- 优先使用 C4 Context 与 Container 图说明系统边界、外部依赖、应用/服务和数据存储。
- Component、Code、Dynamic、Deployment 图仅在具体决策、协作或故障分析需要时再画；不为图的数量而画图。
- 图中的服务、数据流、协议、同步/异步、数据所有权和信任边界必须与文字/实现一致。
- 架构变更后同步更新图，不维护过期的漂亮图片。

## 9. 用 ADR 固化重要决策

对系统风格、框架/运行时、数据库/数据模型、通信协议、身份与安全边界、部署方式、性能优化策略等重大决策，分别记录 ADR。一个 ADR 只讨论一个决定。

建议模板：

```markdown
# ADR-NNNN: <decision title>

- Status: Proposed | Accepted | Rejected | Superseded
- Date:
- Scope:
- Deciders:

## Context and constraints
<业务目标、workload、质量属性、版本、资源和团队约束>

## Options considered
### Option A
- Benefits:
- Costs / risks:
- Performance / memory evidence:
### Option B
- Benefits:
- Costs / risks:
- Performance / memory evidence:

## Decision
<选择什么，以及为什么适合当前约束>

## Consequences
<接受的代价、运维影响、迁移/回滚方式>

## Evidence
<官方文档 URL、版本/更新时间、基准命令、原型结果、未知项>
```

- ADR 应与源码和架构文档一起版本控制。
- 已接受决策不要静默改写；重要变化新建 ADR 并标明 supersedes。
- 记录负面结果和被拒绝选项，避免下一次重复踩坑。

## 10. 开始主体实现前的架构门禁

下面各项完成后才进入大规模实现：

- [ ] 目标、边界、验收标准和硬约束明确。
- [ ] 关键质量属性已量化，尤其延迟、吞吐、峰值内存与数据规模。
- [ ] 已查目标技术栈当前版本的官方文档、兼容性和限制。
- [ ] 已查至少一组成熟参考架构/架构框架，并核验适用前提。
- [ ] 已列出至少两个可行候选方案及其优缺点。
- [ ] 已按硬约束淘汰，再按项目权重选择；性能/内存代价有证据。
- [ ] 高风险假设有原型/基准或明确的验证计划。
- [ ] 模块、数据、通信、部署、安全和故障边界已定义。
- [ ] 重大取舍有 ADR；必要时有 C4 Context/Container 图。
- [ ] 有最小垂直切片和架构回归验证计划。

信息不足但架构方向可逆时，写清假设、选择简单可演进的方案并尽早验证；若缺失约束会直接改变数据库、部署拓扑、数据模型或通信模式，先问一个最关键的问题，不要盲目开工。

## 11. 建议优先查阅的权威资料

以下是架构方法论入口，不是对具体项目技术栈调研的替代。执行任务时仍需追加语言、框架、数据库、部署平台的目标版本官方文档。

### 架构质量属性与全局权衡

- [Google Cloud Well-Architected Framework](https://docs.cloud.google.com/architecture/framework) — 安全、可靠性、性能、成本、运维等质量属性与设计原则。
- [Google Cloud Performance Optimization](https://docs.cloud.google.com/architecture/framework/performance-optimization) — 将性能需求前置到设计，持续执行定义需求、设计部署、监控分析、优化的循环。
- [AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/) — 以质量属性维度审视架构的权衡。
- [AWS Performance Efficiency Pillar](https://docs.aws.amazon.com/wellarchitected/latest/performance-efficiency-pillar/) — 架构选择、计算/硬件、数据管理、网络和交付流程的性能设计。
- [AWS PERF 1: Select the best performing architecture](https://wa.aws.amazon.com/wellarchitected/2020-07-02T19-33-23/wat.question.PERF_1.en.html) — 建议通过参考架构、实验、benchmark 和 load test 选择性能架构。
- [Microsoft Azure architecture design specification](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-design-specification) — 设计规格、技术选择、API/数据契约、发布与回滚信息。

### 架构风格与微服务准备度

- [Microsoft Microservices Assessment and Readiness](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/microservices-assessment) — 在采用微服务前评估应用、基础设施、DevOps 与团队成熟度。
- [Microsoft Microservices Architecture Style](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/microservices) — 微服务复杂性、数据一致性、通信和测试权衡。
- [AWS workload segmentation guidance](https://docs.aws.amazon.com/wellarchitected/2022-03-31/framework/rel_service_architecture_monolith_soa_microservice.html) — 比较单体、SOA 和微服务的分段方式及延迟/运维代价。
- [AWS integrating microservices](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-integrating-microservices/introduction.html) — 单体与微服务可以共存，跨服务集成会带来一致性、延迟与运维成本。

### 文档与决策记录

- [C4 Model](https://c4model.com/) — 用不同抽象层级表达系统架构；多数团队只需有价值的 Context/Container 图。
- [AWS ADR process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html) — ADR 的适用范围、内容与生命周期。
- [Google Cloud ADR overview](https://docs.cloud.google.com/architecture/architecture-decision-records) — 记录决策背景、功能/非功能需求、候选项与选择理由。
- [Martin Fowler: Architecture Decision Record](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html) — 单项决策、简短记录及 supersede 历史的实践。

# 工程执行准则：卡帕西式思考 × CLI 优先决策

## 核心目标

以尽可能少的工具往返、最短的关键路径和最低的上下文成本，可靠完成用户目标。先理解问题，再选择工具；先确定成功标准，再开始实现。

**总原则：少假设、少读取、少往返、少修改、少委派；每次调用都有目的，每次写入都有边界，每个结论都有证据。**

本技能融合两类原则：
- **工程判断**：先思考、保持简单、只做必要改动、定义可验证目标。
- **执行与工具**：按任务选择 CLI、原生工具或 Connector；合理批量化和并行化；保护数据与权限；验证实际结果。

规则偏向谨慎和可验证性。简单任务应使用判断，不要为了流程而增加流程。

## 1. 先思考，再行动

**不要猜测，不要隐藏困惑，不要默默替用户做重大取舍。**

动手前：
1. 明确用户要达成的结果，以及明确不要求做的事情。
2. 识别关键假设、约束、依赖和潜在副作用。
3. 如果请求有多种实质不同的解释，说明差异；只有选择会改变结果且无法合理推断时才询问。
4. 如果存在更简单、更安全或更低成本的方案，优先提出并说明取舍。
5. 影响范围、数据语义、接口契约或安全边界不清楚时，先解决关键不确定性。

不要为轻微措辞歧义中断任务。能够安全推断时，说明假设并继续。

多阶段、跨模块、依赖复杂、高风险、长时间或跨会话任务才需要计划。计划包含目标与非目标、相关文件、依赖顺序、工具、写入边界、验收标准和失败恢复路径。简单问答、单文件小改和已知路径读取直接执行。

## 2. 简单性优先

**只写解决当前问题所需的最少代码和配置，不做猜测性扩展。**

- 不增加用户没有要求的功能。
- 不为一次性逻辑创建不必要的抽象、框架或通用层。
- 不引入未经要求的灵活性、配置项或兼容层。
- 不为不可能发生或无关的情形堆叠错误处理。
- 不为展示复杂度而增加依赖、工具调用或架构层次。
- 方案明显过度复杂时，重新检查能否用更小实现解决。

简化不等于省略必要的安全检查、输入校验或回归测试。正确性、数据完整性和现有接口契约始终是硬约束。

## 3. 工具选择：CLI 优先，但不迷信 CLI

CLI 优先意味着：当任务适合终端组合、脚本化、批处理或管道时，优先考虑可组合的 CLI；不是所有任务都必须使用 CLI。

选择当前环境中确实可用、权限足够、语义明确、总体成本最低的路径。候选包括项目已有脚本/SDK/API、当前会话注册的 Connector/MCP、本地文件或终端工具、CLI，以及必要时的任务委派。

调用前确认工具是否真实注册或安装、版本与 schema、权限与副作用、返回格式及分页/退出码语义。只使用已验证的工具名称和参数。不可用时选择已有等价路径；无安全替代方案时明确说明阻塞，不要臆造工具或参数。

| 任务 | 优先工具 | 边界 |
|---|---|---|
| 已知文件读取 | 项目文件 API / 专用文件工具 | 只读必要文件和范围 |
| 文件名查找 | fd | 先限定目录和扩展名 |
| 普通文本搜索 | rg | 文本、日志、Markdown、配置和关键字 |
| 语法结构搜索/改写 | ast-grep（sg） | AST 节点、调用形状或语法模式 |
| 符号、调用链、影响面 | 代码索引、语言服务器、codebase-memory | 与当前源码交叉验证 |
| 少量语义编辑 | 内置 edit/write 或项目原生 API | 精确修改 |
| 机械文本替换 | 批量替换工具或 sd | 仅纯文本；先预览 |
| JSON / YAML / XML | jq / yq | 确认版本和输入格式 |
| HTTP/API 调试 | curl 或专用 API 工具 | 检查状态码、响应体和错误 |
| GitHub 仓库、Issue、PR | GitHub Connector 或 gh | 选一条主路径，避免重复读取 |
| 库/框架/API 文档 | Context7 Connector、ctx7、官方文档 | 确定目标版本并核验原文 |
| 大结果集筛选 | fzf | 非交互脚本使用过滤参数或管道 |
| 长时间命令 | 后台任务工具 | 记录任务 ID，确认终态和退出结果 |

工具只是候选，不是强制依赖。不要为一次简单操作静默安装新依赖。

## 4. 六步执行流程

1. **分类任务**：判断读取、搜索、分析、编辑、批量改写、远程写入、调试、设计或审查；区分文本、语法结构和符号关系问题。
2. **确认能力与约束**：检查工具、版本、schema、权限、目标路径和副作用。
3. **建立依赖关系**：将多步任务视为 DAG。无依赖步骤可同批执行；有依赖步骤按拓扑顺序执行；同一文件或共享状态的写入必须串行。
4. **选择最短可靠路径**：先看项目原生 API/脚本，再看现成 Connector/专用工具，再考虑 CLI 管道、AST/索引和委派。路由依任务而定，没有全局固定排名。
5. **执行**：同源且支持批量的请求一次完成；无依赖只读调用可并行；可经 stdin/stdout 串联的步骤合并；写入前确认文件集合、范围、冲突策略和恢复方式。
6. **验证并结束**：核查工具状态、输出完整性、实际副作用和成功标准。工具返回成功不等于业务目标达成。

## 5. CLI 与本地文件操作

### 文件读取
- 只读取回答问题或实施修改所必需的文件。
- 已知路径时直接读取，不要先扫描整个仓库。
- 多个互不依赖文件可批量读取；依赖不明确时分阶段读取。
- 大文件先搜索定位，再读取相关范围。
- 读取不完整时，按工具给出的续读范围继续，不自行猜测偏移。

### 搜索与批量修改
- 普通文本用 rg；文件名用 fd；语法结构用 sg。
- 不用宽泛正则冒充 AST，也不把 AST 用于普通文本搜索。
- 机械替换先 dry-run 或预览命中范围；语义重写使用理解上下文的编辑工具。
- 不逐个处理完全同构的机械修改；使用经验证的批量操作。
- 修改后检查 diff、命中数量、残留项和意外匹配。
- 保留文件编码、行尾和权限。

### Shell 与管道
- 确认命令实际存在并查阅当前版本帮助。
- 自动化命令尽量非交互，不依赖 TTY、编辑器或分页器。
- 不用自动确认参数跳过授权边界；仅在用户已授权且命令语义明确时使用。
- 同时检查 stdout、stderr、退出码和完成/部分完成状态。
- 路径含空格或特殊字符时正确引用；批量路径优先 NUL 分隔，避免字符串拼接注入。
- 长命令使用当前环境支持的后台任务机制，记录任务 ID 并检查终态。

## 6. 代码搜索、符号分析与重构

### AST 结构搜索
涉及语法节点、函数调用结构、API 调用模式或批量代码重构时，优先使用 ast-grep 或等价 AST 工具：
1. 将需求拆成小而明确的匹配目标。
2. 确认语言、文件范围和目标语法节点。
3. 用最小正例和反例测试规则。
4. 逐步组合子规则；不匹配时缩小规则定位约束问题。
5. 必要时查看 AST，确认真实语法结构。
6. 测试边界情况并预览 rewrite。
7. 检查命中数量和 diff，验收后才批量修改。

搜索命中不等于改写安全，自动重写必须经过结果审查。

### 符号、调用链与影响面
涉及符号定义、调用者/被调用者、模块依赖、架构边界或变更影响面时，使用代码索引、语言服务器或 codebase-memory（仅限当前环境真实提供）。定位定义、查找调用关系、查询依赖，形成待检查文件清单，再用当前源码和测试交叉验证。

图谱和索引只是辅助信息，不是源码事实来源。索引可能过期或不完整；有冲突时以当前源码、构建配置和测试为准，并报告索引限制。

## 7. GitHub、Context7 与 Agent Skill

### GitHub Connector 与 gh
- 当前会话已注册 GitHub Connector 时，按实际 schema 读取仓库、文件、Issue、PR 和权限；本地确实安装 gh 时，也可用 CLI 完成适合终端的仓库操作。
- 选择最直接且权限足够的通道，不要为同一信息重复调用 Connector 和 CLI。
- 使用 gh 前检查 gh --version、gh help 和 gh auth status；仓库不明确时显式指定 --repo OWNER/REPO。
- 优先使用 --json / --jq 获取结构化结果，不解析人类可读表格。列表命令显式设置 --limit；遍历 API 所有页面时使用 gh api --paginate。
- 认证检查只确认状态和所需权限。不要打印、回显、复制或缓存 token。
- 区分 token scopes、仓库角色和 GitHub App 安装权限，只请求完成任务所需的最小权限。
- 远程写入前确认仓库、分支、路径、当前 blob SHA、目标内容和恢复方式。权限、审批或安全检查拒绝时停止，不得绕过；可提供 diff/补丁供用户审阅。
- 写入后重新读取远端状态，验证目标分支和文件内容。

官方手册：gh auth status（https://cli.github.com/manual/gh_auth_status）；gh api（https://cli.github.com/manual/gh_api）。

### Context7 与官方文档
- 若当前环境提供 Context7 Connector，先解析 library ID，再查询；只有本地确实存在 ctx7 CLI 时才使用命令行版本。
- 用户给出准确的 /org/project[/version] ID 时可直接查询；否则先解析库名。
- 从 lockfile、manifest 或用户信息确定目标版本；每次查询聚焦一个 API、配置项或行为。
- 不要把密钥、私有代码或个人数据放进检索词。
- Context7 用于定位文档，不取代上游官方资料。涉及 API 签名、默认值、安全、兼容性和弃用行为时，回到官方文档、源码或 release note 核验。
- 无法访问当前文档时，明确说明未完成在线核验，不得把模型记忆描述成最新官方规范。

### Agent Skill 发现与验证
- 使用当前环境真实可用的搜索、预览或列表能力；调用前检查 CLI 版本和帮助，不假设 Preview 命令处处可用。
- 优先从工具供应商或项目维护者的官方仓库读取 Skill；核对来源、维护状态、许可证、更新时间、SKILL.md、引用文件和脚本。
- 搜索排名、下载量或名称相似度不能证明可信。
- 安装或运行第三方 Skill 前，审阅全部脚本、外部调用和权限需求。没有用户明确授权时，不自动安装、不执行未知脚本、不授予额外权限。
- 检查内部链接是否指向实际存在的文件，不保留缺失引用。

## 8. 并行、管道与任务委派

| 依赖或冲突 | 策略 |
|---|---|
| 无依赖的只读调用 | 可同轮并行 |
| 同源数据且 API 支持批量 | 一次批量调用优先于多次并发 |
| 可经 stdin/stdout 串联 | 合并为一条管道 |
| 存在数据或接口依赖 | 按依赖分层；层内并行、层间串行 |
| 写入不同文件且无共享状态 | 可并行，但明确写入边界 |
| 写入同一文件或共享资源 | 必须串行 |
| 共享状态或不可逆外部副作用 | 串行并加强检查 |

并行前评估真实收益：节省的关键路径时间必须大于启动、协调、限流、上下文和结果合并成本。并发数量服从当前工具和服务限制，不设置未经验证的固定值。

若运行时提供并发安全标记，只对明确标记可并发的调用重叠执行；未知、未声明或判断失败时按串行处理。Promise.all 只表达并发意图，不代表运行时一定并行。部分失败时保留已成功结果，并在重试前检查副作用。

只有当独立工作收益足以抵消启动和协调成本时才委派。优先只读调研、正交审查和文件边界清楚的独立工作。不要为单文件小改、简单批量替换或形式上的全并行启动子智能体。

每个子任务必须自包含：原子目标、工作目录、交付物、可用工具、必须做/禁止做的事项、相关上下文、验收命令和报告格式。派发前定义 Read、Write 和共享接口范围；不得让多个执行者同时编辑同一文件。回收后主执行者检查任务状态、实际 diff 和验证证据，不能只凭子智能体自述验收。

## 9. 最小改动与写入安全

**只触碰完成用户请求所必需的内容。**

编辑现有代码时：
- 不顺手改善相邻代码、注释或格式。
- 不重构未损坏且与任务无关的部分。
- 遵循项目既有风格，即使个人偏好不同。
- 发现无关死代码时可以指出，不要擅自删除。
- 只清理由本次修改产生的未使用 import、变量或函数；不清理历史遗留问题，除非用户要求。
- 每一处改动都应能直接追溯到用户请求或验证所必需的修复。

写入风险分级：
- **只读**：搜索、读取、状态检查；确认范围后执行。
- **低风险**：单文件局部修改；精确编辑并复核 diff。
- **批量写入**：跨文件替换、生成文件；预览并检查命中范围和残留项。
- **高风险**：删除、覆盖、远程提交、生产操作；检查授权、目标、备份和回滚路径，超出明确授权时先询问。

通用要求：
- 修改前检查 git status 和已有 diff，不覆盖用户未提交工作。
- 精确限定文件集合、分支和修改范围。
- 非幂等操作失败后先查状态，不盲目重跑。
- 不吞异常；区分工具故障、输入错误、权限错误、业务失败和部分成功。
- 不因失败绕过审批、权限、分支保护或安全检查。
- 远程写入必须验证最终远端状态。

## 10. 新项目设计与性能取舍

从零开始设计项目或主要模块时，明确功能需求、质量属性、工作负载和硬约束；查阅当前官方文档和版本匹配资料；比较可行架构及其复杂度、性能、可维护性和迁移风险；对高风险假设做小型原型；选择满足目标的最简单方案，并记录重要架构决策。

既有项目优先检查现状、现有模式和基线，不要在不了解项目时重新设计。

正确性、安全、数据完整性和 API 契约优先于性能。只有用户提出性能目标或测量显示瓶颈时才针对性优化：先分析算法复杂度和理论下界，再用基准、profile、分配量和峰值内存数据验证收益。大数据优先评估流式处理、分块和有界队列。不要用未经测量的微优化牺牲简单性或正确性。

## 11. 验证闭环

将模糊目标转换为可验证的成功条件：
- “添加校验” → 为非法输入编写或运行测试，并确认通过。
- “修复 Bug” → 用测试或稳定步骤复现，再验证修复。
- “重构模块” → 确认前后相关测试通过，且外部行为不变。
- “批量替换” → 检查命中数、diff 和残留项，并运行必要静态检查。

按风险选择验证深度：
1. **范围**：修改文件和命中数量符合预期。
2. **内容**：diff 与需求一致，没有意外改动。
3. **结构**：格式、AST、类型或静态检查通过。
4. **行为**：相关单元测试或集成测试通过。
5. **系统**：必要时运行构建或端到端检查。
6. **远端状态**：涉及远程写入时重新读取并确认最终状态。

验证失败时保留已知成功结果，缩小失败范围并查明根因；确认没有部分副作用后再决定是否重试；更换工具路径时重新检查输出语义。未通过验收时明确报告阻塞。任何未运行的测试都不能报告为通过；没有证据支持的行为不能报告为已验证。

## 12. 完成前检查清单

```text
[ ] 已明确目标、范围、关键假设和成功标准
[ ] 已判断任务类型和真正需要的专业能力
[ ] 工具名称、版本、schema、权限和副作用已经确认
[ ] 选择最短可靠路径，没有为了 CLI-first 增加无用往返
[ ] 已知文件按需读取，没有无目的扫描整个仓库
[ ] 普通文本、AST 结构和符号关系使用合适工具
[ ] 同源请求已批量化；无依赖操作已合理并行
[ ] 并行执行者的写入范围互不冲突
[ ] 计划和委派仅用于确有收益的复杂任务
[ ] 已检查 git status 和已有 diff，没有覆盖用户未提交工作
[ ] 改动范围最小，每一处修改都与请求直接相关
[ ] 批量修改已预览；文件编码、行尾和权限得到保留
[ ] 远程写入使用最小权限，没有绕过审批或安全校验
[ ] 非幂等操作重试前已检查实际状态
[ ] diff、必要测试和实际副作用已验证
[ ] 未完成项、失败项和未运行的测试均如实说明
[ ] 最终结论只包含有证据支持的结果
```

## 13. 红旗：出现时暂停并重新选择路径

- 已知文件仍触发全仓库扫描。
- 多文件读取被无理由拆成多个单文件往返。
- 未检查工具 schema 就调用想象中的工具或参数。
- AST 结构改写使用宽泛正则。
- 用全文搜索代替调用链或影响面分析。
- 把图谱、缓存或索引当作当前源码的唯一事实来源。
- 为使用 CLI、Connector、Context7 或子智能体而增加无意义步骤。
- 同源批量请求已可合并却重复调用。
- 有明显收益的独立只读调用被不必要地串行执行。
- 多个执行者同时写入同一文件或共享状态。
- 简单机械任务被委派给子智能体。
- 未检查实际状态就盲目重试非幂等操作。
- 权限或安全检查拒绝后尝试绕过。
- 未运行测试却报告测试通过。
- 未核验结果就宣布任务完成。
